Отвечай по-русски. Пиши так, чтобы жюри поняло с первого прочтения.

Ты готовишь подачу проекта. Источник правды — **код, а не желания**. Сначала прочитай репозиторий и запусти проект/тесты, чтобы понять, что действительно работает.

## Что делать

1. Прочитай README.md, CLAUDE.md, точки входа, скрипты запуска. Выясни фактическое поведение.
2. Напиши/обнови README.md **строго по официальной структуре организаторов** (см. ниже) — жюри читает именно её.
3. Составь сценарий демо на 2–3 минуты: по шагам, с конкретными входными данными, которые точно дают хороший результат.
4. Напиши текст защиты: проблема → решение → что показываем → какая часть техническая соль → что дальше.
5. Проверь раздел про заранее подготовленные материалы: заготовки, шаблоны, библиотеки, модели, датасеты должны быть перечислены в README.
6. **Напомни координатору про сдачу на платформе.** Запушить в GitHub недостаточно: нужно на странице треков нажать «Сдать решение» и заполнить название и описание проекта. Решение можно обновлять до дедлайна. Пропущенный шаг = работа не сдана.

## Обязательная структура README (список организаторов)

1. Название проекта
2. Краткое описание — какую проблему решает и для кого
3. Что реализовано — основные функции
4. Как работает решение — основной сценарий от входных данных до результата
5. Технологии — языки, фреймворки, библиотеки, AI-модели, API, внешние сервисы
6. Архитектура — основные компоненты и как они взаимодействуют
7. Установка и запуск — пошагово, с реальными командами
8. Как проверить решение — сценарий, который жюри может повторить самостоятельно
9. Данные и интеграции — источники данных, API, внешние сервисы
10. Ограничения — что не реализовано
11. Ссылка на развёрнутую версию, если она есть

Плюс отдельный раздел раскрытия (требование регламента): использованные AI-инструменты и агенты, заранее подготовленные инструкции помощников, шаблоны, библиотеки, модели и датасеты.

## Трассировка требований — обязательная таблица

Отбор в финал проходит **заочно 24–28 сентября**: эксперт открывает репозиторий, нас рядом нет, объяснить ничего нельзя. Его работу надо свести к простановке галочек, а не к раскопкам.

В пункте 8 («как проверить решение») дай таблицу — по строке на каждое обязательное требование кейса:

| Требование кейса | Где реализовано | Как проверить |
|---|---|---|
| <формулировка из кейса> | `путь/к/файлу.ts` | конкретная команда или шаги в интерфейсе |

Требования бери дословно из кейса, не пересказывай своими словами — эксперт сверяет с официальным списком. Невыполненное требование пиши честно в «Ограничениях», а не замалчивай: несовпадение README и кода читается как обман и стоит дороже, чем признанная недоделка.

Первой строкой этого раздела укажи, **что приложение проходит сценарий без API-ключа** на демо-данных. У эксперта нашего ключа не будет, и он должен это увидеть сразу, а не выяснять.

## Формат ответа

```
ОБНОВЛЕНО: <файлы>
ДЕМО-СЦЕНАРИЙ: <шаги с конкретным вводом>
ТЕКСТ ЗАЩИТЫ: <60-90 секунд речи>
ОПАСНЫЕ МЕСТА В ДЕМО: <что может не сработать вживую + как обойти>
ВОПРОСЫ ЖЮРИ: <3 вероятных вопроса + короткие честные ответы>
```

## Ограничения

- **Не приписывай проекту функции, которых нет в коде.** Не успели — так и пиши в README, честно и коротко. Организаторы формулируют это прямо: использовать только то, что подтверждается текущим репозиторием, не выдумывать функции, технологии и результаты.
- Меняй только README.md и файлы документации/демо. Код и конфиги не трогай.
- Не вставляй реальные ключи в README — только имена переменных и пример `.env.example`.
- Не делай commit и push. Не делегируй.
