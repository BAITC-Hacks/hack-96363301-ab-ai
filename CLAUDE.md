Проекты с уже установленными зависимостями. **Начинать с копирования скелета, а не с генератора** — это секунды вместо минут установки и не зависит от скорости сети на площадке.

| Папка | Стек |

Все четыре проверены сборкой. Порядок: скопировать папку, переименовать проект в `package.json` / `pubspec.yaml`, дальше писать код кейса.

Правила, которые легко нарушить:

- **Flutter после копирования — обязательно `flutter pub get`.** В `.dart_tool/package_config.json` абсолютные пути, после переноса они неверные.
- **Копировать через PowerShell или проводник, не через Git Bash.** `mv`/`cp` в bash спотыкаются на симлинках в `node_modules/.bin` и падают с «Permission denied».
- **Новые пакеты в Nest ставить с `--legacy-peer-deps`**, иначе `npm install` падает с `Cannot read properties of null (reading 'edgesOut')`.
- **Prisma только с явной версией** `prisma@5.22.0` — тег `latest` на npm указывает на нерабочий релиз-кандидат `8.0.0-rc.15` без команды `generate`.
- Flutter собирать в **web**, не в APK: жюри открывает ссылку, ничего не устанавливая. Windows-desktop на этой машине сломан и не нужен.

Предпочтения по стеку: бэкенд — Node/TS (Python-проектов у участника нет, FastAPI прогрет лишь на всякий случай); ORM — TypeORM (привычнее в связке с Nest, чем Prisma); фронт — React + Vite + TS + Tailwind.

## Стратегия отбора — два фильтра

Отбор проходит дважды, и фильтры награждают разное.

**Фильтр 1 — 24–28 сентября, заочно.** Эксперт открывает репозиторий, нас рядом нет, объяснить нечего. Решают воспроизводимость и покрытие обязательных требований. Здесь вылетает большинство. **Все пять часов подчинены этому фильтру.**

**Фильтр 2 — Demo Day 29-го, вживую.** Нарратив и убедительность. Готовится после хакатона, времени будет почти неделя. Слайды 23-го не делаем.

Пять приёмов, решающих первый фильтр:

1. **Демо-режим без API-ключа — обязателен.** У эксперта не будет нашего `OPENAI_API_KEY`. Падает или пустой экран без ключа — проект не оценят вовсе. Реальные ответы модели складываем в `fixtures/*.json` по ходу работы; при пустом ключе отдаём их. Демо-путь обязан проходиться целиком без ключа.
2. **Таблица трассировки требований в README:** требование кейса дословно → файл → команда проверки. Эксперт ставит галочки, а не раскапывает. Почти никто этого не делает.
3. **Доказательства в репозитории:** скриншоты или GIF прохода по сценарию — страховка от чужого окружения.
4. **Запуск одной командой.** Меньше шагов — меньше мест сломаться. Если БД не критична для сценария, брать SQLite или файл вместо Postgres.
5. **Видимая агентность:** structured outputs, function calling и лог вызовов модели в интерфейсе. Это отличает агента от промпта в лоб и защищается технически.

Чего не делаем никогда: авторизация и регистрация, роли и права, многопользовательность, своя дизайн-система, мобильное приложение при достаточности веба, инфраструктура, которую надо объяснять. Каждое съедает час и не добавляет ни одного балла по критериям кейса.

- Данные кейса (персональные, конфиденциальные, продуктивные) **не уходят во внешние сервисы** без разрешения организаторов. Для отладки — синтетика.

## Правила координации

- Один файл — один исполнитель. Никогда не выдавай один файл двум агентам.
- Общие интерфейсы (API-схемы, типы, конфиг, схема БД) меняет только координатор.
- Не делегируй ради делегирования: задача на пару правок делается самому быстрее.
- Первая веха всегда — сквозной скелет на заглушках. Наполнение потом.
- Тесты «прошли» только если фактически запущены. Приводи вывод.
- Секреты только в переменных окружения. `.env` в `.gitignore`. В README — только `.env.example`.
- Commit и push делает координатор. Помощники — никогда. Без пустых коммитов и без правки истории.
- Критерии приёмки берутся из официальных критериев оценивания кейса, а не придумываются. Свои добавления помечаются отдельно.
- README оформляется по структуре организаторов из 11 пунктов (см. `hack-pitch`), плюс раздел раскрытия AI-инструментов и заготовок.
