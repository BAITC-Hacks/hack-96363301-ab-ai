# Поиск переформулированных обязанностей

Для функции без текстовой пары агент теперь ищет возможное смысловое соответствие среди функций новой редакции. В демонстрации «Регистрирует все заключённые договоры в едином реестре» сопоставляется с «Учитывает каждое заключённое соглашение в общем перечне», хотя сходство значимых слов равно нулю. Владельцы и обе цитаты восстановлены из документов.

Нажать **«Найти переформулировки»**. Это синтетический комплект из восьми случаев; оба XLSX доступны для скачивания. [Экран компьютера](screenshots/13-semantic-review.png), [экран телефона](screenshots/14-semantic-mobile.png).

## Что получает сотрудник

- Возможная переформулировка: кандидат на сохранение или передачу обязанности.
- Признаки изменения смысла: связанная обязанность с изменением запрета, обязательности, срока или охвата.
- Пара не предложена: модель не нашла соответствия в просмотренной области. Это не доказательство утраты.
- Не проверено: пункт исключён лимитом, ответ отсутствует или не прошёл проверку.

Гипотезы показываются отдельно от исходных статусов функций. Они не изменяют решения пользователя, число потенциальных утрат и отпечаток плана. В Excel добавлен лист «Смысловая проверка» с двумя переходами к точным источникам, моделью и происхождением ответа.

## Воспроизведение

Из каталога `server`:

```sh
npm test
npm run eval:semantic
```

`eval:semantic` по умолчанию отключает API даже при заданном ключе и повторяет сохранённые ответы. Он печатает фактические метрики. **Код выхода 1 ожидаем:** строгий критерий требует 24/24, а известный пропуск даёт 23/24. Тесты воспроизведения отдельно проверяют точное совпадение с сохранённым результатом, включая этот пропуск; их успех не выдаётся за безошибочную классификацию.

Для нового живого сравнения: `npm run eval:semantic -- --live`. Это до шести запросов: проверка исходных меток и смысловой поиск для каждого из трёх комплектов. Результаты могут отличаться; существующие записи не перезаписываются. Параметр `--output путь.json` сохраняет отдельный отчёт нового прогона. Исходный `docs/semantic-evaluation.json` закрепляет измерение, с которым сравнивают тесты воспроизведения.

`OPENAI_MODEL` управляет первоначальной проверкой (по умолчанию `gpt-4.1-mini`), `OPENAI_SEMANTIC_MODEL` — смысловым поиском (по умолчанию `gpt-4.1`). Имя модели входит в ключ записи. Для существующих записей нужны те же байты файлов, имена и модель; пересоздание XLSX может изменить байты архива и сделать запись неприменимой.

## Границы и защита источников

В одном смысловом запросе максимум 12 исходных функций, 80 пунктов новой редакции и 64 000 символов JSON. Цитаты целые, ограничение отражено в охвате. Сходство слов не используется как порог отбора: иначе самые глубокие переформулировки не попали бы к модели. Поиск ограничен распознанными функциями той же области (`unit` или `org`).

Модель выбирает только переданные идентификаторы. Раздельные ветки JSON-схемы требуют либо пару с фрагментами, либо `none` с настоящими `null`. Сервер дополнительно проверяет область, однозначность ответа, принадлежность источников и буквальное наличие фрагментов; владельцев берёт из локального разбора. Локальные сигналы изменения запрета, срока и других условий не позволяют показать пару как эквивалентную. Свободное пояснение модели не принимается.

Смысловой ответ ограничен 4096 токенами, первоначальная проверка — 8192. Тайм-аут одного вызова 45 секунд, автоматических повторов нет. При недоступности API используется подходящая запись либо явно показывается отсутствие проверки. Структурированный ответ и лимит длины основаны на [официальной документации OpenAI](https://developers.openai.com/api/docs/guides/structured-outputs) и [описании лимитов токенов](https://developers.openai.com/api/docs/guides/token-counting); они не гарантируют правильность смыслового вывода.
